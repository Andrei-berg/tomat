# Phase 04.1: Partial Payments at Order Creation - Research

**Researched:** 2026-05-04
**Domain:** Next.js 16 Server Actions + React Client Component form extension + Supabase debt_payments write path
**Confidence:** HIGH

## Summary

Phase 04.1 is a focused gap-closure: the order creation form (`OrderForm`) currently always assigns `status: 'debt'` when `payment_type === 'debt'`, with no mechanism to record a partial upfront payment at creation time. The seller must return to `/debts/[clientId]` later to record any prepayment. This phase adds an optional "partial payment at creation" field to the order form, so the seller can record a prepayment immediately when creating a debt order.

The infrastructure is entirely pre-built: `debt_payments` table exists with RLS, `recordPayment` Server Action is production-ready, `calcEffective` is exported from `dal.ts`, and the `debt_payments.Insert` type is typed in `database.ts`. What Phase 04.1 must do is: (1) conditionally render a "Предоплата" field in `OrderForm` when `paymentType === 'debt'`, (2) extend `createOrder` to optionally insert a `debt_payments` row + update `orders.status` to `'partial'` if a prepayment is given, and (3) handle the `canSave` / UI logic for the new field.

No new packages are needed. All patterns — `useActionState`, `useTransition`, `buildFormData`, `calcEffective`, `debt_payments.insert` + `orders.update` — already exist in the codebase. The implementation is an extension of existing files, not new standalone files.

**Primary recommendation:** Add an optional `prepayment_amount` + `prepayment_type` field pair to `OrderForm` (visible only when `paymentType === 'debt'`), pass them through `buildFormData`, and in `createOrder` handle the insert + status update atomically after order creation succeeds.

### Pattern 1: Prepayment Field in OrderForm (Client Component)
**What:** When `paymentType === 'debt'`, render an optional numeric input for prepayment amount and a payment type selector (cash/card). State is local: `prepaymentAmount: string` and `prepaymentType: 'cash' | 'card'`. Include them in `buildFormData()`.
**When to use:** Only when `paymentType === 'debt'` — hide entirely for cash/card orders.
**Example:**
```typescript
// src/components/ui/order-form.tsx (additions)
const [prepaymentAmount, setPrepaymentAmount] = useState('')
const [prepaymentType, setPrepaymentType] = useState<'cash' | 'card'>('cash')

// In buildFormData():
if (paymentType === 'debt' && prepaymentAmount) {
  fd.set('prepayment_amount', prepaymentAmount)
  fd.set('prepayment_type', prepaymentType)
}

// In JSX (after Section 4 Client, before Section 5 Total+Save):
{paymentType === 'debt' && (
  <div>
    <span>Предоплата (необязательно)</span>
    <input
      type="number"
      min="0"
      step="0.01"
      value={prepaymentAmount}
      onChange={e => setPrepaymentAmount(e.target.value)}
      inputMode="decimal"
      placeholder="0.00"
    />
    <select value={prepaymentType} onChange={e => setPrepaymentType(e.target.value as 'cash' | 'card')}>
      <option value="cash">Наличные</option>
```

### Pattern 2: Extend createOrder Server Action
**What:** After order + order_items insert succeed, check for `prepayment_amount` in formData. If present and valid (> 0 and <= effectiveTotal), insert a `debt_payments` row and update `orders.status` to `'partial'` (or `'paid'` if prepayment covers the full amount).
**When to use:** Only when `payment_type === 'debt'` and `prepayment_amount` is provided.
**Example:**
```typescript
// src/app/actions/orders.ts — additions after order_items insert succeeds

const prepaymentRaw = parseFloat(formData.get('prepayment_amount') as string)
const prepaymentType = formData.get('prepayment_type') as 'cash' | 'card'

if (payment_type === 'debt' && !isNaN(prepaymentRaw) && prepaymentRaw > 0) {
  const effectiveAmt = calcEffective({ calculated_total, discount_percent, manual_total })
  const safeAmount = Math.min(prepaymentRaw, effectiveAmt)

  const { error: prepayErr } = await supabase.from('debt_payments').insert({
    order_id: order.id,
    amount: safeAmount,
    payment_type: prepaymentType === 'card' ? 'card' : 'cash',
  })

  if (!prepayErr) {
    const newStatus = safeAmount >= effectiveAmt ? 'paid' : 'partial'
    await supabase.from('orders').update({ status: newStatus }).eq('id', order.id)
    if (newStatus === 'paid') {
      revalidatePath('/debtors')
    }
  }
  // Non-fatal: order was created successfully; prepayment failure is logged silently
}
```

### Anti-Patterns to Avoid
- **Making prepayment a blocking error:** If the `debt_payments` insert fails after a successful order creation, do NOT delete the order and return an error. The order is already safely saved; a failed prepayment is recoverable via `/debts/[clientId]`. Silently skip the prepayment write on error — or log + continue.
- **Capping prepayment silently in UI:** The UI should show the effective total so the seller knows the cap. Don't let the server silently reduce the amount without feedback.
- **Allowing prepayment > effective total:** Server must cap with `Math.min(prepaymentRaw, effectiveAmt)`. A prepayment of full amount sets status to `'paid'` and removes the order from the debt queue.
- **Showing prepayment section for cash/card orders:** The `debt_payments` table only makes sense for `payment_type === 'debt'`. The field must be conditionally rendered.
- **Forgetting revalidatePath('/debtors'):** If prepayment sets status to `'paid'`, the debtor may disappear from the list; must revalidate.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Effective total calculation | Re-derive formula | `calcEffective()` from `dal.ts` | Already exported, tested, handles manual_total/discount_percent priority correctly |
| Payment type validation | Custom enum check | Literal type guard + `payment_type !== 'cash' && payment_type !== 'card'` | Same pattern used in `recordPayment` action |
| Status computation | Custom logic | `safeAmount >= effectiveAmt ? 'paid' : 'partial'` | Same logic already in `recordPayment` — reuse exactly |
| Form reset after submit | Complex ref/DOM manipulation | `setFormKey(k => k + 1)` + clear prepayment state | Established pattern in `resetForm()` — just add `setPrepaymentAmount('')` and `setPrepaymentType('cash')` |

**Key insight:** The `recordPayment` Server Action already handles the exact same write path (insert `debt_payments` + update `orders.status`). The only reason it cannot be called from within `createOrder` is that `recordPayment` needs an existing `order_id` and uses `useActionState` form binding. The solution is to inline the same 3-step logic (insert → compute status → update) directly in `createOrder` after order creation, not to call another server action.

## Common Pitfalls

### Pitfall 1: Prepayment Failure Rolls Back the Order
**What goes wrong:** Developer wraps the entire `createOrder` in error handling that deletes the order if prepayment insert fails. Order is lost.
**Why it happens:** Treating prepayment as atomic with order creation.
**How to avoid:** Prepayment is best-effort: order creation is the critical path; prepayment is supplemental. If `debt_payments` insert fails, log and continue — return `{ success: true, orderId: order.id }`. The seller can record the prepayment later via `/debts/[clientId]`.
**Warning signs:** Sellers reporting lost orders after partial payment attempts.

### Pitfall 2: Status Left as 'debt' After Full Prepayment
**What goes wrong:** Seller enters an amount equal to the full order total. Order stays in `status: 'debt'`. Appears in debtor list incorrectly.
**Why it happens:** Forgetting to compare `safeAmount >= effectiveAmt` to set status to `'paid'`.
**How to avoid:** Always compute `newStatus = safeAmount >= effectiveAmt ? 'paid' : 'partial'` and apply it when prepayment is recorded. This is identical to the logic in `recordPayment`.
**Warning signs:** Fully prepaid orders appear in `/debtors` with 0 remaining.

### Pitfall 3: calcEffective Not Available in orders.ts
**What goes wrong:** Developer tries to call `calcEffective` in `orders.ts` but gets a "not exported" error. Looking at the Phase 4 RESEARCH.md note ("This function is NOT exported"), they duplicate the logic inline.
**Why it happens:** The Phase 4 research noted it wasn't exported — but it WAS exported as part of Phase 04 implementation (confirmed in current `dal.ts` line 92: `export function calcEffective`).
**How to avoid:** `calcEffective` IS already exported from `dal.ts`. Import it directly: `import { verifySession, calcEffective } from '@/lib/dal'`. Do not duplicate.
**Warning signs:** TypeScript error on import if export was somehow removed.

### Pitfall 4: UI Validation — Prepayment Exceeds Effective Total
**What goes wrong:** Seller enters prepayment of 99999 for a 5000 ₽ order. Server caps it silently, status becomes 'paid', but seller sees no feedback.
**Why it happens:** No client-side max constraint on the input.
**How to avoid:** Set `max={effective}` on the prepayment input in the UI. Display the effective total near the field as a hint. Server still caps for safety (`Math.min`), but UI guides the user.
**Warning signs:** Sellers confused why small orders show "paid" status immediately.

### Pitfall 5: Missing revalidatePath After Prepayment
**What goes wrong:** Order created with full prepayment (status → 'paid'), but `/debtors` still shows the debtor because cache wasn't invalidated.
**Why it happens:** `revalidatePath('/orders')` is already called at end of `createOrder`, but `/debtors` is not.
**How to avoid:** When prepayment results in `status: 'paid'`, also call `revalidatePath('/debtors')`. When `status: 'partial'`, also revalidate `/debtors` since the debtor list balance changes.
**Warning signs:** Stale debtor totals after creating a debt order with prepayment.

### Pitfall 6: prepaymentAmount State Not Reset on Form Reset
**What goes wrong:** Seller saves order, clicks "Новый заказ", but prepayment field retains previous value because `resetForm()` doesn't clear the new state variables.
**Why it happens:** Adding new `useState` without updating `resetForm()`.
**How to avoid:** Add `setPrepaymentAmount('')` and `setPrepaymentType('cash')` to `resetForm()`. The `formKey` increment also remounts the form but state is in closure — explicit reset is required.
**Warning signs:** Prepayment field pre-filled on a fresh form.

## Open Questions

1. **What happens to prepayment if order_items insert fails?**
   - What we know: `createOrder` currently does a compensating delete of the order if `order_items` insert fails. Prepayment is inserted AFTER order_items.
   - What's unclear: No ambiguity — prepayment is inserted only after both order + order_items succeed. The compensating delete only fires if order_items fail (before prepayment).
   - Recommendation: Insert order → insert order_items (on fail: delete order, return error) → insert prepayment (on fail: log, continue, return success). This is the right sequencing.

2. **Should prepayment amount have a client-side maximum validation?**
   - What we know: Server caps with `Math.min(prepaymentRaw, effectiveAmt)`. UI currently has no `max` on the input.
   - Recommendation: Add `max={effective}` to the prepayment input. `effective` is already computed in `OrderForm` as the `effectiveTotal()` result. Show `до {formatRub(effective)}` as placeholder.

3. **Should partial prepayment be allowed on anonymous debt orders?**
   - What we know: `client_id` can be null for debt orders (seller uses `client_name_raw`). `debt_payments` only requires `order_id` — no `client_id` constraint.
   - Recommendation: Yes, allow it. The `debt_payments` write path doesn't require a `client_id`. Anonymous orders with partial prepayment are valid and will appear in `/debtors` under the anonymous debtor bucket.

4. **Should a prepayment that covers 100% of the order show the order in any debt screen at all?**
   - What we know: `getDebtors()` filters `.in('status', ['debt', 'partial'])`. If status becomes 'paid' at creation, the order never enters the debtor queue.
   - Recommendation: This is correct behavior. A fully prepaid "debt" order is an edge case (seller might select 'debt' payment type but then enter full amount as prepayment) — the result is a 'paid' order that never appears as a debt. No special handling needed.
